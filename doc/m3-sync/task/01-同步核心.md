# 01 同步核心（实体 + 文档指纹 + 扫描集成 + 自动扫描 + 孤儿）

> 阶段目标：把"阅读进度"从裸指纹变成**图书侧领域数据**。本阶段不涉及任何 HTTP 协议，产物是实体、服务与扫描钩子；02/03 阶段在其上挂协议与管理面。
> 依据：`doc/m3-sync/调研/01-KOSync协议实证.md` §4（指纹）、`doc/adr/0006-kosync-self-implemented.md`。

## T1.1 实体（`bifrost-domain`）

三张新表 + `Book` 加一列。**新增表由 `ddl-auto=update` 自动创建，无需迁移**；`Book` 加的是可空列，也无需回填脚本（回填逻辑见 T1.3 的 Runner）。

### `sync_account`（表 `sync_account`）

| Java 字段 | 列 | 类型 | 约束 |
|---|---|---|---|
| *(BaseEntity)* `id` / `createdAt` / `updatedAt` | `id` / `created_at` / `updated_at` | INTEGER / BIGINT | PK / NOT NULL |
| `username` | `username` | VARCHAR(64) | NOT NULL **UNIQUE** |
| `encryptedPassword` | `encrypted_password` | VARCHAR(512) | NOT NULL |

- **口令用现有 `PasswordCipher`（AES-GCM 可逆）加密**，与 `User.encryptedPassword` 同机制——R2a 要求管理端**可回显明文**，且校验 `x-auth-key` 需要能还原出口令再算 md5，可逆存储是硬需求。
- Day-one 只有一行（Q3-B）；表结构按"进度属于某个同步账号"设计，未来加多账号不改协议层。

- **唯一约束 `uk_progress_account_document (sync_account_id, document_fingerprint)`** —— 一个同步账号对一份文件只有一行，写入即后写覆盖（LWW，协议语义）。

- **索引**：`@Table(indexes = @Index(name = "idx_progress_book", columnList = "book_id"))`（新表建表时会一并创建，`ddl-auto=update` 对**新表**不吝啬索引；对既有表加索引则不可靠，见 T1.2 的说明）。
- `reportedAt` 语义：写入时取 `Instant.ofEpochSecond(Instant.now().getEpochSecond())`，协议响应用 `reportedAt.getEpochSecond()` **原样回显**（官方是把 `os.time()` 存下来再回显，我们保持同一语义：**秒级、写入后不再变**）。
- `scanAttemptedAt` 是**孤儿生命周期状态机**的载体（见 T1.5）：`bookId == null && scanAttemptedAt == null` = 待结算；`bookId == null && scanAttemptedAt != null` = **固定孤儿**。

- `device_name` 存**最近一次上报的名字**（客户端可改自由文本）；协议没有设备注册，这张表就是"见到过并记录下来的设备"（R6）。

### `Book` 加列（`bifrost-domain/.../entity/Book.java`）

```java
/** 文档指纹：KOSync 客户端对文件内容算出的 partial MD5（32 位小写 hex；未算过 = null） */
@Column(length = 32)
private String partialMd5;
```

- **与既有 `fingerprint`（`path|size|mtime`）是两套东西**，不可互相替代（`CONTEXT.md`「文档指纹」词条）。
- 同时在 `@Table` 上尝试声明 `@Index(columnList = "partial_md5")`：**新库会创建，既有库不保证**（Hibernate `update` 不补既有表的索引）。因此**业务逻辑不得依赖该索引存在**——按 32 位 hex 在家庭规模（千级行）表上全表扫是可接受的，索引只是加分项。

### Repository（`bifrost-domain/.../repo/`）

- `SyncAccountRepository extends JpaRepository<SyncAccount, Long>`：`findByUsername(String)`、`findFirstByOrderByIdAsc()`
- `ReadingProgressRepository`：`findBySyncAccountIdAndDocumentFingerprint(...)`、`findByBookId(Long)`、`findBySyncAccountIdAndBookIdIsNullAndScanAttemptedAtIsNull(...)`、`findBySyncAccountIdOrderByUpdatedAtDesc(...)`（分页用 `Pageable`）、`countBySyncAccountIdAndBookIdIsNull()`、`@Modifying @Query("update ReadingProgress p set p.bookId = null, ... where p.bookId = :bookId")`（删书时摘链，T1.6）
- `SyncDeviceRepository`：`findBySyncAccountIdAndDeviceId(...)`、`findBySyncAccountIdOrderByLastSeenAtDesc(...)`
- `BookRepository` 加：`findByPartialMd5(String)`（返回 `List<Book>`，同名文件多份时取最小 id）、`countByPartialMd5IsNull()`

**事务约定**：`@Transactional` 只出现在 core 服务方法上（与既有约定一致，Controller/Repository 不加）。

## T1.2 文档指纹工具（`bifrost-core/book/DocumentFingerprint.java`）

纯静态工具类，与 `bifrost-common` 的 `Fingerprint`（`path|size|mtime`）并列但**独立**（书侧专用，不上提到 common——避免污染"两套指纹"的语义边界）。

### `partialMd5(Path)` —— 12 点采样

```java
private static final int SAMPLE_SIZE = 1024;
// 采样偏移：0，随后 1024 << (2k)，k = 0..10  → 0,1K,4K,16K,64K,256K,1M,4M,16M,64M,256M,1G
```

- 每点读最多 1024 字节；**读到 EOF 即停止**（后续更靠后的采样点必然也越界，直接 break）。
- 把读到的片段**按顺序**喂给**同一个** `MessageDigest.getInstance("MD5")`，最后 `digest()` → 小写 hex。
- **必须二进制读**：`RandomAccessFile`/`FileChannel`（或 `FileInputStream` + `seek` 用 `FileChannel.position`）。**禁止 `Reader`/`Files.readString`**（换行转换会改变字节流）。
- 空文件 → 空输入做 MD5（按"读到 0 字节就 break"自然得到该结果，不特判）。
- 读失败（IO 异常）→ 返回 `null` 并 `log.warn`，**不抛**（扫描不能因为一个文件算不出指纹而中断）。

### `fileNameMd5(Path)` / `fileNameMd5(String)`

- `md5(basename)`（**仅文件名，含扩展名，不含路径**，对应客户端 `FILENAME` 模式 `main.lua:678-692`）。
- 另提供候选函数 `opdsServedNameMd5(title, extension)` = `md5(title + "." + extension)`——对应 **OPDS 下发到设备时的文件名**（`OpdsController` 用 `title + "." + extension` 作为 `Content-Disposition` 文件名）。两者都只用于**孤儿页的"建议绑定"**（T1.5），不参与主匹配。

### 测试（`DocumentFingerprintTest`）

- 回归黄金值：对 `data-sample/ebook/sample.epub`、`sample.pdf` 生成并固定 MD5 值；
- 边界：空文件、<1024 字节、恰好 1024/4096 字节、12 点全部命中（构造 >1GB 不现实 → 用"文件小于 1GB 时最后几个采样点全部越界"的分支覆盖）；
- 与独立脚本实现互证（脚本不落库，仅开发期一次性比对）；
- **真机核对由用户在自测清单里完成**（见 04 §4）。

## T1.3 扫描集成（`bifrost-core/book/BookScanService.java`）

唯一改动点：**解析后写入 `partialMd5`** + **增量跳过时自愈补算**。

### 改动 1：`applyFields` 之外算指纹（不要在事务里做文件 IO）

`scanLibraryRoot` 的循环里（现 161 行 `String fingerprint = Fingerprint.of(file);` 之后）增加：

```java
String partialMd5 = DocumentFingerprint.partialMd5(file);   // 事务外，与 parser 同级
```

并把 `partialMd5` 加进 `PendingBook` record（现 251-253 行），在 `flush` 里 `b.setPartialMd5(p.partialMd5())`。

### 改动 2：增量跳过分支自愈（现有 162-165 行）

```java
if (!force && existing != null && Boolean.TRUE.equals(existing.getIsAvailable())
        && fingerprint.equals(existing.getFingerprint())) {
    if (existing.getPartialMd5() == null) {
        // 老库升级：指纹未变但文档指纹缺失（或上次读文件失败）→ 只补这一列，不重解析元数据
        pending.add(PendingBook.fingerprintOnly(existing, abs, fingerprint, root.getId(),
                DocumentFingerprint.partialMd5(file)));
        counters.updated++;
        if (pending.size() >= batchSize) { flush(tx, pending); }
    }
    continue;
}
```

- **为什么不能简单地把跳过条件改成 `partialMd5 != null`**：那会让升级后的第一次扫描把整库元数据**重新解析**一遍（等同 `force=true`），而实际只需要补一列。
- `PendingBook` 的 `result` 允许为 null 表示"只补指纹"，`flush` 里 **result 为 null 时跳过 `storeEmbeddedCover`**（现 215 行）。

### 改动 3：`Book` 新增列的赋值

`applyFields`（现 220-244 行）增加 `b.setPartialMd5(partialMd5)`——即把 `partialMd5` 作为参数传入（与 `fingerprint` 同款）。

### 启动回填 Runner（`bifrost-core/book/BookPartialMd5BackfillRunner.java`）

R7 的"启动兜底"：覆盖**从未被扫描碰到**的书（例如库根被禁用、或扫描目录不可达）。

- `@Component @Order(1) implements ApplicationRunner`（`@Order(0)` 已被 `LibraryRootMediaTypeBackfillRunner` 占用）。
- 先 `bookRepository.countByPartialMd5IsNull()`：为 0 直接返回（每次启动成本 = 一条 count）。
- 否则分页取 `partialMd5 == null` 的书，**在事务外**算指纹，用 `TransactionTemplate` 按 `bifrost.scan.batch-size` 批量更新（**不要**用一个长事务包住全库 IO）。
- 文件不存在（`isAvailable=false` 或路径失效）→ 跳过并 debug 日志；下次扫描自愈会再试。
- 读文件失败 → 跳过（不阻断启动）。

## T1.4 同步账号与进度服务（`bifrost-core/book/sync/`）

新增子包 `com.bifrost.core.book.sync`：

| 类 | 职责 |
|---|---|
| `SyncAccountService` | 读写同步账号（创建/改名/改口令/生成随机口令/取账号）；**强制口令 ≠ admin 口令**（R2c）；提供 `verify(username, authKeyMd5)` 供协议层校验 |
| `ReadingProgressService` | 进度的 upsert（LWW）/查询/按书查询/重置（删除）/删除 Book 时摘链；维护 `sync_device` |
| `OrphanProgressService` | 孤儿的结算（扫描后回填）、建议绑定、人工绑定、忽略、人工重新匹配 |
| `ProgressBookMatcher` | 指纹 → Book 的匹配与候选建议（唯一一处匹配算法） |

### 口令与校验（关键实现细节）

- **账号的开箱可用**：`SyncAccountInitializer`（`@Order(2)`，`ApplicationRunner`）在启动时确保账号存在——
  首启自动创建用户名 **`reader`** + **16 位随机口令**（`SecureRandom`，剔除易混字符 `0O1lI`）。
  随机口令天然满足 R2c；用户到管理端「阅读进度」页查看/改名/改口令。幂等，协议开关关闭时跳过。
- `SyncAccountService.verify(username, xAuthKey)`：取账号（用户名不匹配 → 失败）→ `PasswordCipher.decrypt` 还原口令 → `md5(口令)` 小写 hex → 与 `x-auth-key` **常量时间比较**（`MessageDigest.isEqual`，与既有 `SubsonicTokenUtil` 同款）。失败一律返回"未授权"，**不区分用户不存在/口令错**（与官方可观测行为一致，不给枚举探测面）。
- **强制不同**：改口令时若 `md5(新口令) == md5(admin 口令)` 或明文相等 → 拒绝（`BizException.paramError`）。也拒绝把用户名设成与 admin 同名？——**不拒绝**：用户名同名不影响安全（凭据是口令），且用户可能就想叫 admin。但文档提示"建议用不同用户名"。
- 口令生成：`SecureRandom` + 去混淆字符集的 16 位（无 `0/O/1/l/I`），返回值仅经管理端展示（R2a）。

### 进度 upsert（协议 LWW）

```
upsert(accountId, document, progress, percentage, device, deviceId, metadataIgnored):
  existing = repo.findBySyncAccountIdAndDocumentFingerprint(accountId, document)
  now = Instant.ofEpochSecond(Instant.now().getEpochSecond())
  if existing == null:
      row = new ReadingProgress(...); row.reportedAt = now
      row.scanAttemptedAt = null; row.ignored = false
      save;  firstAppearance = true
  else:
      // 无条件覆盖（协议语义：不读旧值、不比较新旧）
      row.progress = progress; row.percentage = percentage
      row.device = device; row.deviceId = deviceId; row.reportedAt = now
      // bookId / scanAttemptedAt / ignored 保持不动
      save;  firstAppearance = false
  touchDevice(accountId, deviceId, device)
  return (row, firstAppearance)
```

- **不做 `metadata` 的任何使用**：客户端默认不发；即便发了也不作为匹配依据（客户端硬约束 11 的同族问题：不可靠）。字段直接忽略。
- 并发：两设备同时首推同一 document → 唯一约束兜底，捕获 `DataIntegrityViolationException` 后**重查再走覆盖分支**（SQLite + WAL，冲突概率低但必须处理，否则会 500）。
- `scan_device` 的 `touchDevice`：不存在则插入（`firstSeenAt = lastSeenAt = now`，`reportCount = 1`），存在则 `lastSeenAt = now`、`reportCount++`、`deviceName = 最新`。

## T1.5 自动扫描与孤儿生命周期（R5 + C1）

### 触发（在 `PUT /syncs/progress` 的同一事务之外）

```java
ProgressUpsert r = progressService.upsert(...);              // 事务内
if (r.firstAppearance()) {
    // ① 即时匹配：库里已经有这本书（绝大多数情况——书就是从我们的 OPDS 下的）→ 直接 AUTO 绑定
    if (!progressService.tryAutoMatch(r.progress().getId())) {
        unmatchedScanTrigger.triggerAsync();                 // ② 未命中才触发扫描；后台，绝不阻塞请求
    }
}
```

> **即时匹配是主路径，扫描是兜底**：按 32 位 hex 查一次 `book.partial_md5` 是纯 DB 查询（毫秒级），
> 覆盖"书已入库"的全部场景；只有"书还没入库"（用户刚拷进目录还没扫）才需要那次后台扫描。
> 实现上 `tryAutoMatch` **不写** `scanAttemptedAt`——"结算"是扫描完成后的动作（T1.5 结算段）。

`UnmatchedProgressScanTrigger`（`bifrost-core/book/sync/`）：

- **无冷却**（C1）；**同一指纹只触发一次**——去重就靠"`firstAppearance` 只在新建行时为 true"，行一旦建立就不会再触发。
- 触发前先 `if (!bookScanService.isScanning())`（T1.5 需给 `BookScanService` 增加 `public boolean isScanning() { return bookScanLock.isLocked(); }`）；**正在扫描则跳过、不排队**。
- 动作：`CompletableFuture.runAsync(() -> bookScanService.scanAll(false))`（沿用现有 `BookRootController` 的异步模式；common ForkJoinPool）。
- **必须吞异常并记日志**：`BizException.scanInProgress`（1100）在竞态下仍可能出现；任何异常都不得冒泡到 HTTP 请求线程。
- 开关：`bifrost.kosync.auto-scan-on-unmatched`（默认 true）。

### 结算（扫描完成事件）

新增监听器 `OrphanProgressSettlementListener`（`bifrost-core/book/sync/`，`@EventListener(BookScanCompletedEvent)`）：

```
for row in repo.findBySyncAccountIdAndBookIdIsNullAndScanAttemptedAtIsNull(...):
    book = matcher.match(row.documentFingerprint)
    if book != null: row.bookId = book.id; row.matchSource = AUTO
    row.scanAttemptedAt = now          // 无论命中与否，都"结算"
    save
```

- `BookScanCompletedEvent` 现有**无消费者**（`CONTEXT.md` 记为"预留 opds-publisher 缓存失效钩子"），本里程碑成为它的第一个消费者。
- 结算**幂等**：`scanAttemptedAt != null` 的行不再被选中。
- 事件是同步发布的（`scanRoot` 内 `publishEvent`）→ 结算在扫描线程里跑；孤儿数量在家庭规模下很小（通常 0–几条），可接受。**注意**：`scanRoot` 的调用方此时已释放 `bookScanLock`（`publishEvent` 在 `finally { unlock }` 之前 —— 实现时确认释放顺序，若在锁内则结算里的任何 `bookScanService` 调用会死锁/1100；结算本身只读仓储，不调扫描，安全）。

### 固定孤儿（此后只能人工）

- 结算后 `bookId` 仍为 null → **固定孤儿**：不再自动匹配、不再触发扫描。
- 管理端能力（03 阶段）：**人工绑定 / 忽略 / 重新匹配**。其中"重新匹配"是人工点一次按钮再跑一遍 `matcher.match`（仍属人工操作，不违反 R5）。
- **删书产生的孤儿**：`DELETE /api/books/{id}` 时调用 `ReadingProgressService.detachByBookId(id)`（`bookId=null`、`matchSource=null`、`ignored=false`、`scanAttemptedAt=now`）——**设为"已结算"**，这样它不会被自动重绑，符合 R5。

### 建议绑定（R5-d）

孤儿页对每条孤儿给出 `suggestedBookId`：用 `fileNameMd5(basename(filePath))` 或 `opdsServedNameMd5(title, extension)` 与孤儿指纹比对，命中的第一本作为建议（**只建议，不自动绑**：设备上的文件名可能被客户端改写，且用户可能手动改过书名）。仅在**查询孤儿列表时按需计算**，不落库。

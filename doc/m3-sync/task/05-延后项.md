# 05 延后项（M3-sync 本轮不做）

> 记录 M3-sync 明确不做/不实现的内容，防止实现时误入；每条都给出"为什么不做"与"将来怎么做"。

## 5.1 书签 / 高亮 / 笔记同步

**KOReader 侧没有同步协议**：标注只能由 `ReaderAnnotation:onExportAnnotations` 导出到书籍旁的 `<book>.annotations.lua` 文件（`readerannotation.lua:255-277`），而 `importAnnotations` 还会拒绝 `device_id` 与本地相同的文件（`:279-283`）——传输方式是"把文件放进共享目录"，不是 API。
**不做的原因**：要做就得改客户端插件（等于维护一个 KOReader fork），与"不自建客户端"的既定取向冲突。
**将来**：`SolAstrius/kosync-rs` 走的是扩展协议 + 配套插件（kosync-ext）；若届时采用，需单独里程碑评估插件分发与版本兼容。

## 5.2 阅读统计（时长/页数）

`statistics.koplugin` 的同步是**整个 SQLite 文件**经云存储插件交换（`statistics.koplugin/main.lua:3095-3105`、`cloudstorage.koplugin/main.lua:197-242`），与 KOSync 无关。
**不做**：它要求 WebDAV/Nextcloud 之类的文件服务（见 5.3），不是本里程碑的能力。
**将来**：先做 WebDAV（5.3），再把统计库同步当作独立特性。

## 5.3 WebDAV

保持 M2-book §5.2 的延后结论。**新的相关性**：它是 5.2 阅读统计同步的唯一可行通道，若将来要做统计，WebDAV 是前置条件。

## 5.4 OPDS-PSE（按页流式）

保持 M2-book §5.3 的延后结论；与进度同步无耦合。**将来做 PSE 时**可获得一个副产品：服务端能在 acquisition link 上下发 `pse:lastRead`，让 KOReader 打开书时自动落到上次页（`opdsbrowser.lua:840-859`）——这需要与本次的进度数据打通，但**客户端只消费、不回传**，所以只能"服务端 → 设备"单向下发。

## 5.5 多用户 / 多同步账号

Day-one 只有一行同步账号（Q3-B）。表结构已按 `sync_account_id` 维度设计，加多账号时：管理端点支持列表、设备自行选择账号（协议层用户名即可区分），**协议层无需改动**。

## 5.6 Readest 的验收与 Readest **Web 版**的 CORS

- Readest 桌面版（Tauri）不受 CORS 约束，填自定义 server 即可；**不进本里程碑验收门槛**（Q4），只要求"不被我们破坏"（响应形状严格按协议，不做任何自创字段）。
- **Readest Web 版**跑在浏览器里：若它直连本服务，需要给 KOSync 安全链开 CORS（当前只有 `/api/**`、`/rest/**` 链挂了 `.cors()`）。**Day-one 不开**——给协议端点开跨域会扩大攻击面，且没有验证过 Readest Web 是否真的会带 `Origin`。将来若要用，按 `bifrost.cors.allowed-origins` 的既有配置方式显式放开。

## 5.7 FILENAME 模式作为主指纹

客户端 `checksum_method = FILENAME` 时 `document = md5(basename)`，与内容指纹是两套值。本轮**只把文件名指纹用于孤儿页的"建议绑定"**（T1.5），**不建**"文件名 → 书"的主映射。
**原因**：设备上的文件名可能被客户端或用户改写（OPDS 下发用的是 `title + "." + extension`，侧载则是用户自己的命名），不可靠；把它当主映射会产生"错误地匹到另一本书"的静默错误，比孤儿更糟。

## 5.8 进度历史与多设备时间线

只保留"最后一处位置"（协议语义）。想要"设备 A 在 3 天前读到 40%，设备 B 现在读到 42%"这种时间线，需要每次上报都留一版历史行——**服务端可以做到**（协议不禁止），但会带来保留策略、列表分页与"哪条算当前"的额外复杂度。
**将来**：如确有需求，加 `reading_progress_history` 表（只增不改），当前表仍只存最新一条。

## 5.9 跨格式续读（同一本书 EPUB ↔ PDF）

**协议层不可能**：客户端跳转只用 `progress`（XPointer / 页码），而第三方格式的位置串互不通用；客户端也**没有百分比 → 位置的兜底**（调研档 §3 硬约束 2）。服务端把 A 格式的位置回给 B 格式，结果只会是"跳不动"或"跳到错误位置"。
**结论**：不做，也不做"看起来像支持"的兜底（这正是被否决的 Q2-C 方案，记录在 ADR-0006）。

## 5.10 严格复刻官方协议行为

有意**不**复刻的部分（均有理由，记录以免后人当作 Bug）：

| 官方行为 | 我们的做法 | 原因 |
|---|---|---|
| 缺 `Accept` 头 / 版本不认 → **412** + `{code:100..102}` | 不校验 | 客户端总是发送该头；额外的校验只增加失败面 |
| 错误码 2000–2005 段 | 用 Bifrost 图书保留段 **3000+** | 客户端只按 HTTP 状态码判定，`message` 仅展示（硬约束 12）；不照抄官方错误文案（ADR-0006 的 AGPL 纪律） |
| `X-Framework: gin/0.2.0` 响应头 | 不设置 | 无客户端读取；伪装框架无意义 |
| 空 body 的 POST/PUT → 500 | 400 + 明确 message | 更准确；客户端不会发这种请求 |
| 未知 document 的 GET → `200 {}` | **一致**（不做"改进"成 404） | 404 会让客户端显示笼统错误而不是"没找到进度" |

## 5.11 既有问题：`book.file_path` 唯一索引从未生效

`Book` 的 `@UniqueConstraint(name = "uk_book_filePath", columnNames = "filePath")` 用了 **Java 属性名**而非物理列名，导致 `data/bifrost.db`、`data/hurl.db` 里**都没有这个唯一索引**（唯一性目前仅由 `BookRepository.findByFilePath` 的应用逻辑保证）。
**本轮不修**：① 与本里程碑无关；② 给既有表补唯一索引需要先做去重，`ddl-auto=update` 也不会补。
**将来**：单独一次"命名修复 + 去重脚本 + 索引建立"的维护任务（新库从此刻起就会带索引，老库需显式处理）。

## 5.12 定时扫描

`bifrost.scan.cron`（默认 `0 3 * * *`）**声明了但从未被消费**（无 `@EnableScheduling`/`@Scheduled`）。本轮不接线：自动扫描由"未匹配的新进度"触发（R5/C1），定时全库扫描与它重叠且会带来"半夜 IO"的争议。

## 5.13 协议增强（我们自己的扩展端点）

如 `/syncs/progress` 的列表查询、批量删除等——**不加**：任何新端点对 KOReader 都不可见（客户端 `api.json` 是固定的），只会成为无人调用的死代码。管理类需求一律走 `/api/book-sync/**`。

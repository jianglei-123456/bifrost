## 关键事实速查

| 事实 | 出处 |
|---|---|
| KOReader/Readest 都接受 OPDS 1.x Atom（KOReader 也支持 2.0 JSON，**但 1.x 是 safe baseline**） | 02 / 04 |
| OPDS 1.2 规范的图片 link 例子使用**根相对 href**，客户端按 feed URL 解析 | 02 §3 |
| KOReader 客户端**只看 `rel="http://opds-spec.org/acquisition"` 触发下载** | 02 §1 |
| KOReader 不支持 OPDS Digest 认证（仅 Basic） | 02 §1 |
| EPUB 规范明确：多作者 = 多 `<dc:creator>` 兄弟元素（非分隔符串） | 03 §1 |
| Calibre 生态用 ` & `（带空格）做多作者拼接；epublib API 返回 `List<Author>` 需自己 join | 03 §2/§3 |
| `com.positiondev.epublib:epublib-core:3.1` 在 Maven Central；`nl.siegmann.epublib:epublib-core` 不在 Central | 03 §3 |
| OPDS `rel="http://opds-spec.org/image"` 指向同 server 动态抽取端点，**Readest 和 KOReader 都能消费** | 04 §1/§2 |
| Calibre content server 自身就发**根相对动态端点**（`/get?what=cover`），与本设计模式一致 | 04 §4 |

## 与项目既有约束的契合点

- `bifrost-core/com.bifrost.core.book` 包已存在（`package-info.java`："电子书元数据解析"），与 M1 music 路径对称。
- `bifrost-adapter/opds-publisher` 模块已存在（`package-info.java`："生成图书 OPDS 流（Atom/XML）"），为占位。
- `MediaType` 枚举已预留 `BOOK` 值。
- 项目精神"不做提前抽象——book 落地时再演进"被本调研论证为正确选择（见 ADR-0004）。

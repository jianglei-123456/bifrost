# 05 延后项（M2-book Day-one 不做）

> 记录 M2-book mini-milestone 明确延后/不做的内容，防止实现时误入。

## 5.1 进度同步（KOSync）

> **已由 M3-sync 承接（本节仅作历史记录保留）**：新里程碑见 `doc/m3-sync/`（调研档 `doc/m3-sync/调研/01-KOSync协议实证.md` + 任务档 `doc/m3-sync/task/`）与 `doc/adr/0006-kosync-self-implemented.md`。
> 本节下方的延后理由中，**理由③"自建价值低"已被推翻**（官方实现不认识"书"、零管理 API，给不了书级语义）；另：下方引用的调研档里"`PUT` 返回 **202** = 旧进度拒绝覆盖"**是错的**——官方 2016 年 `73b9d53` 已删除该分支，客户端收到 202 会判失败并把推送丢回离线队列（勘误表见新调研档 §7）。

调研档 `doc/m2-book/调研/01-KOReader生态与OPDS.md` §一 详细描述 KOSync 协议（4 端点 + 2 自定义头）。**M2-book Day-one 不实现**：

- 端点 `/users/create` / `/users/auth` / `PUT /syncs/progress` / `GET /syncs/progress/:document` 不挂
- KOReader 端"Progress sync"功能**不工作**（不会连到本服务）；用户需继续用官方 `sync.koreader.rocks` 或后续接入

**延后原因**：
1. 调研档方案 C 列了"最小 8 端点"包括 KOSync 4 端点，但本轮用户决策是 Day-one **只做图书导入 + 元数据处理 + OPDS 分发**（Q1），进度同步不在范围。
2. partial MD5 算法跨格式不稳（调研档 1.5 / 1.4），实现后还需 Book 实体侧加 `partialMd5` 字段 + 客户端 UI 层调优，**深度超过本轮**。
3. 第三方参考实现成熟（kosync-dotnet / 官方 koreader-sync-server），自建价值低。

**未来接入路径**：
- 后续里程碑可单独建 `bifrost-adapter/kosync-server` 模块（仿 `opds-publisher` 路径）
- 实体层 `Book` 已预留 `fingerprint` 字段（path+size+mtime），与 partial MD5 是**两套指纹**——partial MD5 走 `progress_partial_md5` 单独存储
- 不影响本轮 OPDS 端点结构

## 5.2 WebDAV

KOReader 内置 `cloudstorage.koplugin/providers/webdav.lua` 支持 WebDAV 整目录浏览。**Day-one 不实现**：

- 不挂 WebDAV server（通常在 `/webdav/books/` 路径）
- 用户若需要整目录浏览，仍用 FTP 客户端或直接 SMB/NFS 共享文件目录

**延后原因**：OPDS 已覆盖"按元数据浏览/搜索/下载"，WebDAV 是"整目录传输"——家庭场景下 OPDS 已够用，WebDAV 是服务器/极客向。

## 5.3 OPDS-PSE（按页流式阅读）

针对漫画 / 图像书按页流式（`rel="http://vaemendis.net/opds-pse/stream"`）。**Day-one 不实现**：

- 不发 PSE stream link
- 漫画 / 图像 PDF 用户仍需整本下载

**延后原因**：用户本轮目标是"整本下载可读"；PSE 需要服务端 PDF 渲染 + 切片 + per-page endpoint，工作量 > 2 周；漫画资源**多数家庭自托管不优先**。

## 5.4 多用户

- KOSync 协议层有用户概念（每用户独立进度）；本项目 Day-one 不实现 KOSync，故多用户**自然延后**
- OPDS 端点 Day-one **可匿名**（Q6-C）；若开启 `require-auth` 也仅复用 admin 单账密（与 `/api/**` 共享 `UserRepository`）
- **不引入** Subsonic 的多用户角色映射、用户创建、用户库权限

## 5.5 一书多格式

**Day-one 一书 = 一文件**（Q12 决策，不引 BookFile 子表）。

未来如需支持（"Pride and Prejudice EPUB 版 + PDF 版合并为一个 Book"）：
- 加 `BookFile` 子表（1:N）
- 扫描时按"主标题 + 主作者"规范化匹配
- OPDS acquisition feed 一 entry 多 link
- **当前不引入**

## 5.6 系列（Series）作为独立实体

**Day-one Series 是 Book 的字段**（Q3-B），不独立建 Series 实体。

未来如需"按系列浏览"（Series as 聚合维度）：
- 加 `Series` 实体 + `Book.seriesId` FK
- OPDS 加 `/opds/v1.2/catalog/series` 导航 feed
- 复用 music `AlbumKey` 模式的规范化

## 5.7 PDF 首页渲染（封面抽取增强）

**Day-one PDF 无内嵌缩略图时 `embeddedCover=null`**（Q31 决策）。

未来如需 PDF 首页作为封面：
- `PDFRenderer.renderImageWithDPI(0, 72)` 输出 JPEG
- 加进 `BookCoverService.parsePdfCover()`（`parseEpubCover` 已存在）
- 缩略图用 72 DPI（更快）或 150 DPI（更清晰）
- 单文件耗时 +50-200ms，**事务批大小可能要调小**（200 → 50）

## 5.8 元数据写回

**Day-one 元数据编辑只改 DB，不写回 EPUB/PDF 文件**（与 music "不写回标签" 一致）。

未来如需（"在 Calibre 里能看到我编辑过的书名"）：
- EPUB 写回：解压 ZIP → 改 `content.opf` → 重新打包
- PDF 写回：PDFBox `PDDocument.save()` 写 XMP/InfoDict
- 复杂度高 + 风险大（损坏文件），**不做提前规划**

## 5.13 OPDS 2.0 JSON feed

KOReader 实际**也支持 OPDS 2.0**（`Accept: application/opds+json`）——**Day-one 不发 OPDS 2.0**。理由：

- 1.x Atom 已覆盖 KOReader + Readest
- 2.0 JSON 与 1.x Atom **维护两套模板成本高**
- KOReader `parseFeed` 先 JSON 后 XML 回退，1.x 始终可用
- 未来如客户端有诉求，加 2.0 JSON Controller（Atom 模板 → JSON 映射），不影响 1.x

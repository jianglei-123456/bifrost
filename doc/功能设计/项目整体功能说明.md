## 1. 产品定位与目标

**Bifrost** 是一个**家庭自托管的媒体库管理平台**，统一管理三类媒体资源：**视频 / 音频（音乐）/ 电子书**。

本平台的核心定位：

1. **以"文件即事实"为原则**：媒体文件存放在用户自有目录中，目录结构**不强制规范**（用户痛恨强制目录结构），Bifrost 以**文件标签（Tag）为主、文件名为兜底**的方式解析元数据，构建可浏览、可搜索、可播放的媒体库。
2. **自建协议服务，直连客户端**：平台自身提供 **Subsonic 兼容协议服务（Syrinx）**，让整个 Subsonic 客户端生态（Feishin、DSub、Symfonium、play:Sub、Supersonic 等）**直连 Bifrost** 播放与管理音乐，不依赖任何外部服务。
3. **开放的管理契约**：平台通过 REST API（`/api/**`）暴露全部管理能力，**管理端前端（Vue Dashboard）在另一个独立项目开发**，本平台只负责定义契约与功能规划。
4. **离线优先**：元数据全部来自本地标签解析，不依赖联网刮削即可完整使用；在线增强作为后续里程碑。

> 里程碑约束：**本轮（v1）只交付「通用能力 + 音乐管理 + Subsonic 服务」**，使系统具备初步可用性——能够管理音乐文件，并让支持 Subsonic 协议的客户端对接使用。视频、电子书、Jellyfin、OPDS 均作为后续规划（见第 4 章）。

## 2. 目标用户与使用场景

| 用户 | 场景 |
| --- | --- |
| 家庭管理员 | 在一台常开的电脑/NAS/服务器上部署 Bifrost，把散落在各硬盘、NAS 目录里的音乐文件（MP3/FLAC/M4A，中文歌为主）挂为库根，一次性扫描建立媒体库 |
| 家庭其他成员 | 用手机/桌面客户端（DSub、Symfonium、play:Sub、Feishin 等）连接 Bifrost 的 Subsonic 服务，浏览艺术家/专辑、搜索、播放、收藏、评分、建歌单 |
| 平台使用者（开发向） | 通过管理 REST API 或未来的 Dashboard 查看扫描状态、管理库根、浏览媒体库、管理歌单 |

典型场景：

- **S1 首次建库**：管理员配置库根（可多个，如 `D:\Music`、`E:\Lossless`）→ 触发扫描 → 艺术家/专辑/曲目自动聚合入库 → 客户端连接即用。
- **S2 日常增量**：往目录里拷入新歌 → 手动触发或定时扫描 → 新曲目自动入索引，无需全量重建。
- **S3 客户端播放**：家庭成员用手机 App 连接 Bifrost，浏览中文歌手的拼音索引分组、搜索歌曲、流式播放、收藏/评分、创建歌单。
- **S4 数据备份**：SQLite 数据库文件与封面缓存位于可配置数据目录，Docker 部署时挂载宿主卷，直接备份该目录即可。

### 3.1 通用能力（本轮交付）

详见《通用功能说明》。要点：配置管理、日志、统一异常与响应、定时任务、媒体库根与扫描框架、持久化（SQLite）、统一认证体系、REST 契约、适配器框架、健康检查、事件机制。

### 3.2 音乐管理（本轮交付）

详见《音乐管理功能说明》。要点：

- 支持 MP3（ID3v2.3/2.4）、FLAC（Vorbis Comment）、M4A/AAC（MP4 atoms），WAV 无标签兜底可播；WMA/APE 明确不支持。
- 手动触发 + 定时增量扫描（路径+大小+mtime 指纹），缺失文件标记隐藏、保留歌单引用。
- 艺术家/专辑**全局聚合**（跨库根同名专辑合并为一个实体），曲目归属库根；`getIndexes` 按库根过滤。
- **中文拼音首字母索引**（v1 内置，多音字按短语词典处理；日文等其他字符归 `#`）。
- 封面：内嵌图 > 目录图（cover.jpg/folder.jpg），`getCoverArt` 支持缩略图缓存。
- 播放统计（playCount/lastPlayed）、收藏（starred）、评分（1–5）、静态歌单。
- **Subsonic 服务（Syrinx）**：Subsonic API 1.16.1 线协议 + OpenSubsonic 合规，v1 实现约 28 个端点，见《音乐管理功能说明》8.2。

### 3.3 媒体类型规划（后续）

| 媒体类型 | 规划能力 | 归属包/模块 | 状态 |
| --- | --- | --- | --- |
| 视频 video | 媒体扫描、索引（作为扫描框架的第二个消费方） | `com.bifrost.core.video` | 后续里程碑 |
| 电子书 book | 元数据解析、OPDS 发布 | `com.bifrost.core.book` / `opds-publisher` | 后续里程碑 |

> v1 的媒体库根与扫描框架按**可扩展**设计（`MediaType` 枚举预留 `VIDEO/BOOK`），但**不做提前抽象**——音乐垂直先跑通，video/book 落地时再演进。

### 3.4 对外集成

| 集成 | 本轮 | 说明 |
| --- | --- | --- |
| **Subsonic 协议服务（Syrinx）** | ✅ 交付 | Bifrost 自身成为 Subsonic 兼容服务端，客户端直连 `/rest/**` |
| Jellyfin 推送 | ❌ 预留 | 适配器框架定义接口与事件钩子，实现待定 |
| OPDS 图书流 | ❌ 预留 | 同上 |
| 原 sonic-client（向外部 Sonic 推送） | ❌ 移除 | 方向反转：Bifrost 即服务端，模块更名为 syrinx |

### 3.5 管理端（另一项目）

管理端前端（Vue Dashboard）在**独立项目**开发，消费本平台 `/api/**` REST 契约。其功能规划见《音乐管理功能说明》第 9 章，包含：媒体总览、库根管理、扫描管理、媒体浏览与搜索、歌单管理、收藏/评分、账号设置、系统信息。

## 4. 里程碑规划

| 里程碑 | 内容 | 验收标准 |
| --- | --- | --- |
| **M1（本轮 v1）** | 通用能力 + 音乐管理 + Subsonic 服务（Syrinx）+ 管理 REST API + SQLite + Docker | ① 扫描 MP3/FLAC/M4A 建库；② Feishin/DSub 等客户端可连接、浏览、搜索、播放、收藏、评分、建歌单；③ `/api/**` 契约可用；④ 六份文档齐备 |
| M2 | 视频管理（扫描/索引）与 video 浏览；管理端 UI（另一项目）首版 | 视频库可浏览、可被 Dashboard 管理 |
| M3 | 在线元数据刮削（MusicBrainz/Last.fm）；转码（ffmpeg）；文件系统监听实时增量 | 音乐元数据自动补全；客户端可请求转码播放 |
| M4 | 电子书管理 + OPDS 发布；Jellyfin 推送/同步 | 图书流可被阅读器订阅；视频库可同步到 Jellyfin |
| M5 | 多用户体系；动态歌单；播放历史明细；音频指纹去重；OpenSubsonic 扩展增强 | 见《各文档可增强章节》 |

> 里程碑为规划性质，随产品演进可调整。

## 5. 非目标（本轮明确不做）

| 非目标 | 说明 |
| --- | --- |
| 不强制目录结构 | 任意松散目录即可建库，不做"艺术家/专辑/曲目"规范目录校验 |
| 不写回标签 | v1 只读解析文件标签，绝不修改源文件元数据 |
| 不做转码 | Subsonic 服务直出原始文件；`maxBitRate/format` 参数接收但忽略 |
| 不做在线刮削 | 不依赖网络补全元数据（离线可用优先） |
| 不做视频/电子书 | M1 只交付音乐；video/book 仅框架预留 |
| 不做 Jellyfin/OPDS 实现 | 仅适配器框架与占位模块 |
| 不引入 Redis/MyBatis/WebFlux/Actuator | 保持依赖最小化（技术架构约束） |
| 不做多用户 | v1 单管理员账号（表结构预留） |
| 不做音频指纹去重 | 文件去重按路径指纹（路径+大小+mtime） |

## 6. 术语表

| 术语 | 含义 |
| --- | --- |
| 库根（Library Root） | 一个挂载进媒体库的顶层目录，对应 Subsonic 的 musicFolder |
| 扫描（Scan） | 遍历库根文件系统，解析标签、构建/更新媒体索引的过程 |
| 指纹（Fingerprint） | 识别文件是否变更的标记：路径 + 文件大小 + 最后修改时间 |
| 聚合（Aggregation） | 把曲目归并为艺术家/专辑实体的过程；跨库根全局聚合 |
| 全局聚合 | 同名专辑/艺术家在不同库根中合并为同一个实体 |
| Subsonic API | 音乐流媒体服务器生态的 REST 协议（基线 1.16.1） |
| OpenSubsonic | 社区维护的 Subsonic API 开放演进规范（澄清/扩展/新增） |
| Syrinx | Bifrost 的音乐网关模块名（潘神排箫），内含 subsonic-api 实现 |
| ID 前缀 | Subsonic 实体 ID 形式：`ar-`（艺术家）、`al-`（专辑）、`tr-`（曲目）、`pl-`（歌单） |

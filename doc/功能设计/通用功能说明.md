## 1. 概述与范围

本文档描述 Bifrost 的**通用（公共）横切功能**——即与具体媒体类型无关、被所有业务垂直（音乐、后续的视频/电子书）共享的能力。这些能力构成平台的公共底座。

覆盖范围：

1. 配置管理
2. 日志
3. 统一异常与响应
4. 定时任务
5. 媒体库根与扫描框架（通用）
6. 持久化（SQLite + Spring Data JPA）
7. 认证体系
8. REST API 约定
9. 适配器框架
10. 健康检查
11. 事件机制
12. 可增强内容

> 技术实现细节（类、包、配置键）见《整体技术架构》与《音乐管理技术设计》；本文档聚焦"功能层面"。

## 2. 配置管理

### 2.1 配置来源与优先级

| 优先级（高→低） | 来源 | 说明 |
| --- | --- | --- |
| 1 | 环境变量 / 启动参数 | 覆盖 yml；用于敏感项（初始密码、加密主密钥）与容器部署 |
| 2 | 覆盖配置文件 | 通过 `SPRING_CONFIG_ADDITIONAL_LOCATION` 指定的外部 yml（Docker 场景挂载 `/data/application.yml`） |
| 3 | 内置 `application.yml` | 默认值（`bifrost-bootstrap` 模块） |

### 2.2 配置项组织

配置统一以 `bifrost.*` 前缀组织，通过 `@ConfigurationProperties` 绑定为强类型配置类。主要分组：

| 分组 | 内容 |
| --- | --- |
| `bifrost.db` | SQLite 数据库文件路径 |
| `bifrost.library` | 库根列表（name/path/enabled；`mediaType` 区分音乐/图书） |
| `bifrost.media` | 封面缓存目录等媒体通用配置 |
| `bifrost.scan` | 扫描事务批大小、定时扫描 cron（已声明但无调度实现，见第 5 章） |
| `bifrost.auth` | 初始管理员账号（用户名固定、密码经环境变量注入）、加密主密钥 |
| `bifrost.subsonic` | Subsonic 服务开关、对外宣称的 API 版本 |
| `bifrost.opds` | OPDS 是否要求 HTTP Basic（`require-auth`，默认 false=匿名） |
| `bifrost.kosync` | 阅读进度同步（M3-sync）：`enabled` 协议开关、`registration-enabled` 自助注册、`auto-scan-on-unmatched` 未匹配指纹自动扫描一次、`public-base-url` 展示给用户抄进设备的地址（留空则按当前主机名+端口拼） |
| `bifrost.cors` | 允许的跨域来源（`allowed-origins`，默认放行全部；空列表=禁用 CORS） |

> 完整配置键表见《整体技术架构》第 6 章 /《音乐管理技术设计》第 10 章。

### 2.3 敏感配置

- **初始管理员密码**：仅通过环境变量 `BIFROST_AUTH_INITIAL_PASSWORD` 注入，**不落 yml、不进仓库**；首次启动时写入数据库（加密存储），后续以数据库为准。
- **口令加密主密钥**：优先环境变量 `BIFROST_AUTH_SECRET`；未提供时自动生成随机密钥并写入数据目录 `secret.key`（含启动警告，提示生产环境应显式配置）。

## 3. 日志

- 基于 Spring Boot 默认 **Logback**，无需额外依赖。
- 输出：控制台 + 文件（数据目录 `logs/` 下按日滚动，保留策略可配置）。
- 级别：全局默认 INFO；`com.bifrost` 下关键流程（扫描、Subsonic 认证）支持按包调整。
- 约定：扫描/聚合/认证等关键节点打 INFO/DEBUG 日志；错误统一走异常体系（见第 4 章），由全局处理器记录。

## 4. 统一异常与响应

### 4.1 管理 REST（`/api/**`）

统一响应信封：

```json
{
  "code": 0,          // 0 = 成功；非 0 = 业务错误
  "message": "ok",    // 错误时为人类可读信息
  "data": { ... }     // 业务数据（成功时）
}
```

| 约定 | 说明 |
| --- | --- |
| HTTP 状态码 | 成功 200；参数错误 400；未认证 401；无权限 403；不存在 404；服务器错误 500 |
| 业务错误码 | `code` 非 0：1000 参数错误、1001 资源不存在、1002 未认证、1003 无权限、1004 冲突/状态非法、1100 扫描进行中、1200 内部错误（预留段：2000+ 音乐领域、3000+ 视频/图书领域） |
| 异常体系 | 自定义 `BizException(code, message)`；未知异常由全局 `@RestControllerAdvice` 兜底转 500 |

### 4.2 Subsonic 端点（`/rest/**`）

错误遵循 Subsonic 协议：**HTTP 200 + `status="failed"` + `<error code message/>`**（见《Subsonic_API_参考》第 3 章）。两类错误体系互不混用。

## 5. 定时任务

- **定时扫描尚未接线**：`bifrost.scan.cron`（默认 `0 3 * * *`）已声明但无调度实现（无 `@EnableScheduling` / `@Scheduled` 消费方），因此当前**只能手动触发**——管理端 `POST /api/music-roots/scan/all` 或 Subsonic `startScan`；定时扫描待增补（见第 6.2 节）。
- 扫描执行互斥：同一媒体类型同一时刻只允许一个扫描运行（锁见第 6 章）。
- 扫描完成后发布事件（见第 11 章），供下游订阅（如 Subsonic 缓存失效）。

## 6. 媒体库根与扫描框架（通用）

### 6.1 库根（LibraryRoot）

- 库根（`library_root` 表，`mediaType` 列区分音乐/图书）是**音乐与图书共享的持久化概念**：管理端把音乐侧称为「音乐目录」、图书侧称为「图书目录」，两者同表、由 `mediaType` 隔离。
- 一个库根 = 一个挂载进媒体库的**顶层目录**，由用户配置（name + path + enabled）。
- 支持**多个库根**：音乐目录如 `D:\Music`（我的音乐）、`E:\Lossless`（老唱片），图书目录同理；每个库根独立记录扫描时间与状态。
- 音乐目录对应 Subsonic 的 **musicFolder**（`getMusicFolders` 输出、`getIndexes` 可按 folder 过滤）；图书目录对应 OPDS 图书集合。
- 音乐目录禁用（enabled=false）后不参与扫描，其曲目对客户端隐藏。

### 6.2 扫描触发方式

| 方式 | 说明 |
| --- | --- |
| 手动触发 | 管理 REST `POST /api/music-roots/scan/all`（全部音乐目录）或 `POST /api/music-roots/{id}/scan`（单个目录）；Subsonic `startScan` 同样触发 |
| 定时扫描 | ❌ 待增补——未接线（`bifrost.scan.cron` 已声明但无调度实现，见第 5 章） |
| 文件监听 | ❌ 可增强（WatchService 实时增量） |

- **待增补（定时扫描）**：`bifrost.scan.cron` 已声明但无任何调度实现（无 `@EnableScheduling` / `@Scheduled`），当前只有手动触发路径——管理端或 Subsonic `startScan`；定时增量扫描待增补。
- 触发语义：音乐扫描**同步**（`POST /api/music-roots/{id}/scan` 阻塞至结束并返回最终 `ScanStats`），图书扫描**异步**（立即返回 SCANNING，轮询 `/api/book-roots/scan/status`）。

### 6.3 扫描状态与并发

- 每个库根有扫描状态：`IDLE / SCANNING / 上次结果（时间、统计：新增/更新/缺失/错误数）`。
- **同一媒体类型同一时刻只允许一个扫描**（音乐/图书各自独立互斥锁，可并行；无论手动/Subsonic 触发），后到者返回"扫描进行中"。
- 单个目录内**顺序遍历**文件（v1 不做线程池并发，数千曲目量级足够）；多个目录串行执行。
- 扫描**幂等、可中断重启**：随时可再次触发，重复扫描不产生脏数据（按指纹增量）。

### 6.4 变更检测指纹

- 指纹 = `路径 + 文件大小 + 最后修改时间(mtime)`。
- 指纹相同 → 跳过（不重解析标签）；不同 → 重新解析入库；文件消失 → 标记缺失。

### 6.5 缺失文件处理

- 文件消失后曲目标记 `isAvailable=false`，**从浏览/搜索/播放列表对客户端隐藏**，但**保留记录与歌单引用**（避免歌单条目漂移）。
- 提供手动清理能力（管理 REST），彻底删除缺失记录（可增强：自动清理策略）。

### 6.6 对媒体类型的扩展性

- `MediaType` 枚举：`MUSIC`（本轮）、`VIDEO`、`BOOK`（预留值）。
- 扫描框架定义通用阶段（枚举文件 → 指纹比对 → 解析入库 → 聚合 → 发布事件），**各媒体类型通过策略/服务实现各自解析**。
- 约束：**不做提前抽象**，video/book 落地时再演进框架；本轮只保证枚举与包结构预留。

## 7. 持久化（SQLite + Spring Data JPA）

### 7.1 选型

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 数据库 | **SQLite 单文件**（`org.xerial:sqlite-jdbc` + `hibernate-community-dialects`） | 家庭单机零运维；单文件便于备份 |
| ORM | **Spring Data JPA**（Hibernate） | 与 `bifrost-domain` 的 Repository 接口规划吻合；开发效率高 |
| 文件位置 | `bifrost.db.path`（默认 `./data/bifrost.db`），可配置 | Docker 挂载宿主卷即完成备份 |

### 7.2 规则

- Repository 接口定义在 **`bifrost-domain`**，实现由 Spring Data 生成；Service（`bifrost-core`）只依赖接口。
- 事务边界在 core 的 Service 方法上（`@Transactional`）；扫描为大批量写操作，按"文件批次提交"控制事务粒度。
- SQLite 注意点：启用 WAL 模式、设置 busy_timeout，避免读写互斥；字段映射避免使用 SQLite 不支持的类型。
- Schema 演进：v1 采用 `ddl-auto=update`（简化）；后续引入迁移工具（可增强，见第 12 章）。

## 8. 认证体系

### 8.1 账号模型

- v1：**单一管理员账号**（用户名：配置指定 `bifrost.auth.initial-username`，默认 `admin`）。
- `User` 表结构预留多用户扩展（username 唯一、角色字段预留）。

### 8.2 口令存储

- **可逆加密存储（AES-GCM）**：规范要求服务端能还原明文以验证 Subsonic 令牌（`token = md5(password + salt)`），因此**不能只存单向哈希**（Ampache/Navidrome 同款做法，详见《Subsonic_API_参考》2.2）。
- 主密钥来源：环境变量 `BIFROST_AUTH_SECRET`，缺失则生成随机密钥落 `data/secret.key`（600 权限）并警告。

### 8.3 认证方式（双端统一账号）

| 入口 | 认证方式 |
| --- | --- |
| Subsonic `/rest/**` | ① 令牌认证 `t=md5(password+salt)` + `s`（推荐，v1.13+ 客户端）；② 密码认证 `p`（明文或 `enc:` 十六进制，兼容老客户端） |
| 管理 REST `/api/**` | ① HTTP Basic（用户名+密码）；② 与 Subsonic 同款 t/s 令牌（同一账号） |

- 认证失败：Subsonic 返回 `HTTP 200 + status=failed + error 40`；管理 REST 返回 `HTTP 401 + 信封 code=1002`。
- 安全建议：对外暴露走 HTTPS（反向代理）；`p=enc:` 只是十六进制编码，不是加密。

## 9. REST API 约定（`/api/**`）

### 9.1 通用约定

| 项 | 约定 |
| --- | --- |
| 前缀 | `/api/**`（`/api/ping` 保留自 v1.1） |
| 格式 | JSON（UTF-8），请求/响应均 JSON |
| 信封 | 见第 4.1 节 `{code, message, data}` |
| 命名 | 资源复数名词，如 `/api/music-roots`、`/api/albums`；详情 `/api/albums/{id}` |
| 分页 | 列表接口统一 `page`（从 0 起）/`size`（默认 20，最大 200）查询参数，返回 `{total, items}` |
| 过滤 | 排序/过滤参数按资源定义（如 `sort=title`、`q=关键词`） |
| 时间 | ISO-8601 UTC |

### 9.2 端点总览（v1）

| 分组 | 端点 |
| --- | --- |
| 系统 | `GET /api/ping` |
| 音乐目录 | `GET/POST /api/music-roots`、`GET/PATCH/DELETE /api/music-roots/{id}`、`POST /api/music-roots/{id}/scan`（同步） |
| 音乐扫描 | `POST /api/music-roots/scan/all`（同步）、`GET /api/music-roots/scan/status` |
| 浏览 | `GET /api/artists`、`GET /api/artists/{id}`、`GET /api/albums`、`GET /api/albums/{id}`、`GET /api/tracks`、`GET /api/tracks/{id}` |
| 搜索 | `GET /api/search?q=` |
| 歌单 | `GET/POST /api/playlists`、`GET/PUT/DELETE /api/playlists/{id}`、`POST /api/playlists/{id}/entries`、`DELETE /api/playlists/{id}/entries/{entryId}` |
| 标注 | `POST /api/starred`、`DELETE /api/starred`、`PUT /api/rating` |
| 账号 | `GET /api/user`、`PUT /api/user/password` |

> 业务语义见《音乐管理功能说明》第 9 章（管理端功能规划即消费这些端点）。

## 10. 适配器框架

### 10.1 定位

`bifrost-adapter` 聚合模块承载"对外部客户端/服务的适配"：

```
bifrost-adapter
├── syrinx                    # 音乐网关（本轮实现）
│   └── subsonic-api          # Subsonic 协议服务端实现（/rest/**）
├── jellyfin-client           # 占位模块（视频配套，待定）
└── opds-publisher            # 占位模块（图书 OPDS 流，待定）
```

### 10.2 框架机制

- 适配器通过**事件钩子**与核心联动：订阅"扫描完成"等事件，执行自身同步/失效逻辑（v1 中 subsonic-api 订阅扫描完成事件刷新缓存）。
- 预留通用适配器接口定义（名称待定），jellyfin/opds 落地时实现；**本轮不做提前抽象**。
- 约束：适配器可依赖 `bifrost-core`，禁止反向依赖（见《整体技术架构》第 4 章）。

## 12. 事件机制

基于 Spring `ApplicationEventPublisher` 的进程内事件：

| 事件 | 载荷 | 订阅方 |
| --- | --- | --- |
| `MusicScanCompletedEvent` | 音乐目录（`libraryRootId`）、统计（新增/更新/缺失/错误） | subsonic-api（缓存失效）、未来适配器 |
| `TrackUpdatedEvent`（预留） | 曲目 id | 后续扩展 |

事件为**同步/异步可配**：v1 同步发布（保证扫描完成即数据一致）；重负载时可切异步（可增强）。

## 13. 可增强内容

| 方向 | 说明 |
| --- | --- |
| 文件系统监听 | WatchService 实时增量扫描，事件驱动即时入库 |
| 多用户体系 | 开放用户管理、角色（adminRole/settingsRole 等 Subsonic 角色映射） |
| API Key 认证 | OpenSubsonic `apiKeyAuthentication` 扩展，服务器生成不透明令牌、可只存哈希 |
| 数据库迁移工具 | Flyway/Liquibase 管理 SQLite schema 演进，替代 `ddl-auto=update` |
| 指标与监控 | 引入 Actuator/Prometheus：扫描耗时、端点 QPS、认证失败告警 |
| 扫描并发 | 多目录并行扫描、断点续扫 |
| 异步事件 | 事件异步化，降低扫描完成路径延迟 |
| 中央日志收集 | 结构化日志 + 日志轮转策略增强 |
| 管理端 UI | 由另一项目提供 Vue Dashboard 消费 `/api/**` |
